## 1. Яку задачу розв'язує SQL і хто його користувач

SQL (Structured Query Language) — це предметна мова для роботи з реляційними базами даних: даними, що зберігаються в таблицях із рядками й стовпцями. Вона дозволяє створювати таблиці, додавати й змінювати дані та, найважливіше, **ставити запитання до даних**: «скільки замовлень зробили клієнти з Харкова цього року?», «хто з клієнтів витратив понад 1000 грн?».

Головна ідея SQL — **декларативність**: користувач описує, *що* він хоче отримати, а не *як* це знайти. Не потрібно писати цикл по рядках, вибирати алгоритм пошуку чи думати про файли на диску. Вибір способу виконання бере на себе СУБД (PostgreSQL, MySQL, SQLite та інші).

Кінцеві користувачі SQL різні:

- **розробники** бекенду, чиї програми щодня надсилають запити до бази;
- **аналітики даних**, які будують звіти без програмування в загальному розумінні;
- **адміністратори баз даних**, які створюють структуру таблиць і стежать за швидкістю;
- **тестувальники й підтримка**, яким треба швидко перевірити, що лежить у базі.

Це саме предметна мова (DSL), а не мова загального призначення: у SQL немає класів, звичайних циклів і виведення на екран; зате в ній є все потрібне для вибірки, групування й зв'язування даних.

## 2. Мінімальний робочий приклад

Уявімо маленький інтернет-магазин із двома таблицями: клієнти й замовлення.

```sql
CREATE TABLE customers (
    id   INTEGER PRIMARY KEY,
    name TEXT NOT NULL,
    city TEXT
);

CREATE TABLE orders (
    id          INTEGER PRIMARY KEY,
    customer_id INTEGER NOT NULL REFERENCES customers(id),
    amount      NUMERIC NOT NULL,
    created_at  DATE NOT NULL
);

INSERT INTO customers VALUES
  (1, 'Олена', 'Харків'), (2, 'Іван', 'Київ'),
  (3, 'Марія', 'Харків'), (4, 'Петро', 'Львів');

INSERT INTO orders VALUES
  (1, 1, 700, '2026-02-10'), (2, 3, 500, '2026-03-05'),
  (3, 2, 300, '2026-01-15'), (4, 2, 900, '2026-04-20'),
  (5, 4, 200, '2025-12-30'), (6, 1, 150, '2026-05-01'),
  (7, 4, 400, '2026-02-02');
```

Запит: *показати міста, у яких клієнти цього року зробили замовлень більше ніж на 1000, — з кількістю замовлень і сумою, від більшої суми до меншої.*

```sql
SELECT c.city,
       COUNT(*)      AS orders_count,
       SUM(o.amount) AS total
FROM orders o
JOIN customers c ON c.id = o.customer_id
WHERE o.created_at >= '2026-01-01'
GROUP BY c.city
HAVING SUM(o.amount) > 1000
ORDER BY total DESC
LIMIT 3;
```

Результат:

| city   | orders_count | total |
|--------|--------------|-------|
| Харків | 3            | 1350  |
| Київ   | 2            | 1200  |

```sql
SELECT c.name,
       SUM(o.amount) AS total_spent
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY total_spent DESC;
```

Результат:

| name   | total_spent |
|--------|-------------|
| Іван   |       1200  |
| Олена  |       850   |
| Петро  |       600   |
| Марія  |       500   |

Якщо потрібні й клієнти без замовлень:

```sql
SELECT c.name,
       COALESCE(SUM(o.amount), 0) AS total_spent
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name
ORDER BY total_spent DESC;
```

LEFT JOIN залишає всіх клієнтів зі списку ліворуч, а для тих, у кого немає замовлень, стовпці orders будуть `NULL`.
SUM від одних NULL дає NULL, а не 0, тому `COALESCE(..., 0)` замінює його на нуль.

Різниця між `WHERE` і `HAVING`: `WHERE` фільтрує окремі рядки *до* групування, а `HAVING` фільтрує групи *після* нього. Тому `SUM(...)` у `WHERE` написати не можна: на цьому етапі сум ще немає.

## 3. Одне вдале й одне невдале рішення в синтаксисі

### Вдале: запит читається майже як речення, а спосіб виконання схований

Синтаксис SQL вибудовано навколо ключових слів, схожих на англійську: `SELECT ... FROM ... WHERE ... GROUP BY ... ORDER BY`. Фактично я пишу «вибери оце, з цього, де виконується така умова». Я не вказую, як шукати, з якої таблиці починати та чи користуватися індексом. Цим займається оптимізатор запитів: він сам обирає порядок з'єднання таблиць і спосіб пошуку.

Наслідки цього рішення: аналітик без глибокого програмування може написати корисний запит; той самий запит лишається коректним, коли таблиця виросте з тисячі рядків до мільйона (СУБД просто обере інший план виконання); а один і той самий SQL-код у більшості випадків працює на різних СУБД.

### Невдале: порядок написання не збігається з порядком виконання

Запит пишеться починаючи з `SELECT`, але СУБД обчислює його зовсім в іншому порядку: `FROM` → `JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Через це виникають пастки, які інтуїтивно не очевидні. Наприклад:

```sql
SELECT amount * 2 AS double_amount
FROM orders
WHERE double_amount > 1000;   -- помилка
```

Здається логічним: я ж щойно дав стовпцю ім'я. Але `WHERE` виконується *раніше* за `SELECT`, і на цьому етапі псевдоніма `double_amount` ще не існує, тому PostgreSQL повідомить, що такого стовпця немає. Правильно писати `WHERE amount * 2 > 1000`. (Частина СУБД, зокрема SQLite і MySQL, допускає такий запис як послаблення, і це ще одна ілюстрація того, що діалекти відрізняються.) Така ж плутанина виникає між `WHERE` і `HAVING`: початківці намагаються використати агрегатну функцію у `WHERE`. Мова виглядає як проста англійська мова, але під цим виглядом ховається власна, відмінна від читання зверху вниз, логіка, і саме це багатьох збиває з пантелику.

## 4. Чим це робилося б без SQL і чому було б гірше

Без SQL дані довелося б зберігати у файлах (скажімо, CSV або JSON) і писати програмний код для кожного запитання. Для мого прикладу це був би цикл по всіх замовленнях: відфільтрувати за датою, знайти клієнта кожного замовлення, скласти суми в словник за містами, відкинути малі, відсортувати.

Чим це гірше:

- **Багато коду на кожне запитання.** Вісім рядків SQL перетворюються на десятки рядків програми, у яких легко припуститися помилки.
- **Швидкість.** Програма читає весь файл у пам'ять і перебирає всі рядки. СУБД використовує індекси й оптимізатор, тому на великих обсягах різниця величезна.
- **Узгодженість даних.** У файлах ніхто не стежить, що `customer_id` справді вказує на існуючого клієнта. У SQL це гарантують обмеження (`REFERENCES`, `NOT NULL`, `PRIMARY KEY`).
- **Одночасна робота багатьох користувачів і транзакції.** Файл, який одночасно пишуть двоє, легко зіпсувати. СУБД гарантує, що група змін виконається повністю або не виконається взагалі.
- **Спільна мова.** SQL знають аналітики, розробники й адміністратори, тому всі можуть працювати з одними й тими самими даними однаковим способом.

## 5. Межі мови

SQL чудово підходить для вибірки й зв'язування табличних даних, але має чіткі межі:

- **NULL і трійкова логіка.** Відсутнє значення `NULL` не дорівнює навіть самому собі: вираз `city = NULL` ніколи не спрацює, треба писати `city IS NULL`. Умови з `NULL` дають не «так» чи «ні», а ще й «невідомо», і це постійне джерело помилок.
- **Діалекти.** Базовий SQL стандартизований, але вже обмеження кількості рядків відрізняється: `LIMIT` у PostgreSQL/MySQL/SQLite, `TOP` у SQL Server, `FETCH FIRST` у стандарті. Тому «один і той самий SQL всюди» — лише частково правда.
- **Складна логіка.** Умови, цикли, рекурсія й обхід графів у SQL незручні: потрібні рекурсивні вирази (`WITH RECURSIVE`) або процедурні розширення, які в кожній СУБД свої.
- **Неструктуровані дані.** Для документів, графів чи великих потоків подій SQL — не найкращий вибір.
- **Безпека.** Якщо збирати запит у програмі склеюванням рядків із введення користувача, виникає SQL-ін'єкція.

Наприклад:

```python
name = input("Введіть ім'я: ")
query = "SELECT * FROM customers WHERE name = '" + name + "'"
```

Якщо ввести рядок `' OR '1'='1`, у запит потрапить:

```sql
SELECT * FROM customers WHERE name = '' OR '1'='1'
```

Умова `'1'='1'` завжди істинна, тому запит поверне усіх клієнтів.

Що б я робив, упершись у ці межі: складну логіку виніс би в код програми або збережені процедури; для запобігання ін'єкціям використовував би параметризовані запити, а не склеювання рядків; для документів чи графів розглянув би спеціалізовані бази (MongoDB, Neo4j); для звітів із складним порядком обчислень розбивав би запит на частини через `WITH`.

## 6. Чому я обрав саме цю мову

Я обрав SQL, бо це одна з найпоширеніших предметних мов у розробці: з нею стикаються майже в кожному проєкті, де є дані. Вона добре ілюструє, що таке DSL: у ній немає нічого зайвого, зате те, що є, дозволяє коротко виразити складні запитання. Також на SQL зручно показати і сильні, і слабкі боки мови: декларативність як вигоду і розбіжність між записом і виконанням як ціну за неї.
